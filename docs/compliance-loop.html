The Compliance Loop

The design system is stated three times: as prose a model reads, as a static rule with an id, and as a test against a rendered page. Every skill ends in a checker run, every finding carries the address of the paragraph that fixes it, and the exit code decides when the work is done.

tokens.css · src/system

The two-layer model

Everything downstream depends on one rule: no visual value is ever written as a literal. A value is named twice before it is painted.

Design tokens name the available values. --space-16, --radius-md, --surface-neutral. A theme sets them, and the three set skills move them along their own scales.

Semantic properties name the visual roles inside one component and reference a token. --card-padding: var(--space-16). The component's CSS reads the property, never the token. The editor rewrites the assignment, and because the assignment stays a token reference, a theme change reaches the component.

A page sits outside that chain. It declares no properties of its own and reads design tokens directly, so a page inherits the theme without holding any of it.

.claude/skills

Nine skills, bundled with the package

The skills ship inside the npm tarball and live-tokens setup-claude installs them into a consumer project. They divide into authoring and verification.

  • create-theme reads one request, derives one design direction, and routes a color intent, a type intent, and a geometry intent to set-colors, set-type, and set-geometry. Each of those three changes one dimension and nothing else.
  • create-page assembles a page from shipped components at their defaults. It calls pick-component when two components could fit, and create-component when the catalogue lacks one.
  • create-component delivers a runtime file, an editor file, a registration, and a contract together.
  • check-compliance reads one npx live-tokens report run, classifies every finding as mechanical, judgement, or deliberate, and hands the fix list to fix-findings. It edits no file.
  • fix-findings edits the files the checkers name, groups the work by rule, and re-runs until both checkers exit 0.

The skills carry what a checker cannot decide: which layout suits a reading task, which component in a confusable family, which separator is the smallest one that separates. The checkers carry what prose cannot enforce: whether the file actually does it.

bin/

Two checkers, static and rendered

Both checkers emit findings in one shape: a stable rule id, a file, a line, and a fix slug. That shape is what makes the loop mechanical, because a skill can parse --json, repair, and re-run against the exit code.

The static half

check-page reads a page source. check-component reads a runtime file, its editor, and its registration. Severity is a project decision: live-tokens.config.json sets it per rule, and --off, --warn, --error, and --strict move it for one run. report aggregates both and adds signals no rule covers, such as a token a component declares and never reads, a component with no registration, and a pending tokens.css migration.

The token vocabulary

Both checkers open by loading the project's vocabulary: every custom property declared in its own tokens.css, plus every semantic property declared in a component's :global(:root) block. That set is read from the project rather than compiled into the package, so a project running an older tokens.css is measured against the names it actually has.

A name outside the set is a finding, and the message depends on the shape of the name. A name matching one of the 25 scales the token contract governs is reported as a rename to chase in tokens.css, because a name with that shape and no declaration behind it is a typo. A name opening with a state, such as --hover-surface, is told that a state is a segment of a property name and never a token of its own. Anything else is reported as neither a design token nor a semantic property.

src/testing · bin/contractRunner.mjs

Three runs behind one verdict

Without --tests, both checkers stop at the source. With it, a skill's verification step is a machine verdict on a running app. A model asked to review its own component will tell you the theme reaches it. Playwright changes the theme and measures the pixel.

The registry contract, under Vitest

Node and happy-dom, no browser, because these are wiring questions and none of them need a paint. The run imports the module the project names as registrySetup, a module that registers components and stops there. Importing an editor does not register it, and importing the app entry point would mount the app.

This is the second of the three places a token is checked. The static rules ask whether the name exists. Vitest asks whether it is wired: declared, seeded, and reachable. Playwright asks whether it paints.

Per registration it asserts that the entry is sound, declared, and seeded. Across the run it asserts that every component authored in the project is registered at all.

The registry checks 8
  • selectionThe run selects at least one component: the one requested, or every registered one.
  • coverageEvery component authored under src/system/components is registered.
  • source filesourceFile resolves to a real file, and the schema is not empty.
  • no duplicatesNo variable is declared twice in the schema.
  • declaredEvery editable token in the schema is declared in the runtime's :global(:root) block.
  • seededEvery editable token is seeded in component-configs/<id>/default.json.
  • opacity floorA token with a minimum opacity seeds at or above it.
  • alias round tripOne alias survives a round trip through the editor store.

It runs first for a reason. A component missing from the registry reports that one fact, instead of six preview failures all caused by the missing entry.

The eight obligations, under Playwright

The 26 component contracts are data, one file per component, naming that component's parts, states, persistence cases, and theme expectations. A single suite drives every contract through the same eight tests, in a serial describe so the first failure stops the cascade.

Two of those carry most of the weight, because they are the two no reading of the source can settle.

Persistence drives a real control, reads the painted value before and after, saves, reopens the editor, then reads back both the stored value and the repainted preview. It finishes by asserting that the reset variable no longer holds its shipped value, because a Reset that cannot tell the shipped baseline from the saved one passes every naive version of this test.

Theme projection is the third place, and the one that closes the chain. A name can exist in tokens.css, be declared in the runtime, be seeded in the config, and still never reach a pixel. This is the test that catches that. It previews a theme and asserts three things at once: every variable declared to change moved, every variable declared to hold stayed, and every aliased pair still resolves to one value. Then it cancels the preview and asserts that every watched variable is back where it started. A component that paints from a literal survives the first half and fails the second.

Page compliance, under Playwright

The page suite runs the five page-* rules in the ledger above. It opens the project's own route, taken from the pages object in the file that imports LiveTokensRouter, at each viewport the testing settings name. It reuses the component contracts: the parts and paint expectations that check a component in the editor are the same ones it looks for on the page.

A rule that cannot apply returns a reason rather than a pass. At 390px the grid rule reports that the page is one column, below the 768px the grid needs, and that sentence lands in the coverage table where a reader can see it.

The run itself

Determinism is mostly setup. The project's data directory is copied to a temporary directory with _working.json, _active.json and _production.json removed, so no run reads or writes live editor state and no two runs share a baseline. The Playwright config is generated rather than borrowed. The child process gets a deadline, and on a signal the runner stops the child before removing the directories it is still writing into.

Then the mapping. A result becomes a finding by its position in the suite, not by its title, so rewording a test cannot silently detach it from the rule it reports under. Every result also becomes a coverage row: passed, flaky, or inapplicable with the reason. Reconciliation compares that coverage against the full rule set, and a component and rule pair with no result at all becomes a tests-incomplete finding. tests-not-installed, tests-setup and tests-incomplete are the three rules a run can never silence. Nothing passes by not running.

This is the division of labour worth copying. The skills carry the judgement: which component fits the reader's task, which layout, which token for a role. The suites carry everything a machine can settle, and they return an exit code rather than an opinion. A skill that ends in a model reviewing its own diff has no verdict in it. A skill that ends in --tests --strict until exit 0 does.

the walkthrough

One page, one new component

Here is the whole path for the case you asked about: a page that uses a shipped component, needs one that does not exist yet, lays both out, and is checked until it passes.

  1. Read the project. The route table in App.svelte, --columns-count in the vendored tokens.css, and the catalogue from npx live-tokens components, which lists shipped and project components alike with the usage comment each one carries.
  2. Name the sections before the columns. Read the page top to bottom, name each section by what the user reads, types into, or presses, and take its column spans from the layout that matches the reader's task. Each section is a row of the page grid.
  3. Match each need to a component. When two could fit, pick-component applies a decision test written for that family. When nothing fits, create-component authors one.
  4. Author the component as three files and a contract. A runtime file whose :global(:root) block declares one semantic property per editable value, each assigned a token; an editor file exporting the schema; a registration; and a ComponentContract that names the component's parts. Without the contract, --tests reports contract-missing.
  5. Check the component alone. npx live-tokens check-component <id> --tests --strict runs that one id through the static rules, the registry contract under Vitest, and the eight editor obligations under Playwright. Repeat until exit 0 with complete coverage.
  6. Assemble. Components at their shipped defaults, page CSS in design tokens, one text style per element, one primary action, one space step per position, and a route whose source entry is what makes Page Source work.
  7. Verify the page. report for the static picture, then check-page <file> --tests --strict, which opens the page's own route in a browser and proves what only a rendered page can.
  8. Loop. Findings go to fix-findings by rule, largest error group first. Re-run both. Then --strict, which promotes every warning to an error.
  9. Read the page yourself. One h1, no skipped heading levels, copy at 45 to 90 characters, containers aligned at the bottom, the primary action last. The checkers cannot see a layout.
tests/e2e · scripts/

How the rules prove themselves

A rule that cannot fail proves nothing, and a skill that names a flag the CLI dropped hands the model a command that exits 1. Both classes of drift have happened here, so both are now gated.

The gates

  • Defect fixtures. tests/e2e/contract-defects and page-defects fail every rule once on a fixture written to fail it, and pass it once on the exception the rule reserves. They are the only pages in the repository carrying a defect on purpose, and they are kept out of the shipped project so a consumer never runs them.
  • Checker unit tests. bin/check-page.test.ts and check-component.test.ts drive the static rules directly, about 2,000 lines between them.
  • check:skills. Twenty-five rules over the prose itself: frontmatter name matches the directory, the body stays under 250 lines, every reference file is named and every named reference exists, every npx live-tokens <verb> is one the CLI dispatches, every flag the CLI offers on that verb is named by the skill, no retired flag survives, no flag is attributed to the wrong verb, every sibling skill named is bundled, and every dispatched verb reaches some skill or is exempted with a written reason.
  • check:skill-atlas and check:skill-sources. The editor renders each skill as a diagram whose nodes cite SKILL.md by line number. Anchor text repairs a range that moved and refuses one whose anchor is gone.

All of it sits in prepublishOnly, alongside four smoke runs that install the tarball, scaffold a project, and run both test paths end to end.

The smoke runs 4

Each packs the real tarball and installs it into a throwaway project outside the repository.

  • check:smoke-installA minimal Vite app that mounts the editor installs the tarball and builds with no special config.
  • check:smoke-createThe shipped live-tokens create scaffolds an app, which installs without --legacy-peer-deps and builds.
  • check:smoke-component-testsTwo projects built from the create template validate a component they authored with check-component --tests, covering registration, contracts, defects, and isolation.

The reverse direction is the one that costs. --carry-from shipped in the CLI and in --help and reached no skill, so two set-colors runs silently carried the first theme's fonts and geometry into the second. A flag its own skill never names is a flag the model never reaches for, which is why the verb and flag checks run in both directions.

why it holds

One loop, three statements of the same contract

The prose tells the model what to build. The static rule catches the shape. The rendered test catches the cascade, which is the only place a design system actually fails: a component that stops repainting when the theme moves, a run of text that drifts off the shipped styles, a pair that misses AA, a section that leaves the grid.

The finding is what makes it a loop. It is an address: a rule, a file, a line, and the name of the paragraph that fixes it. The model runs the command, reads the address, edits, and runs again, until the exit code is 0 and the only work left is the work a person has to look at.
